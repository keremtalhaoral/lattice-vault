# Security Policy

> **Prototype — do not use in production.** This document describes what the code in this repository
> actually does today. Items marked **(planned)** do not exist yet. The project has **not** had an independent
> security audit.

## Reporting a vulnerability
- Please report privately via **GitHub private vulnerability reporting** (repository → *Security* →
  *Report a vulnerability*). **Do not open public issues, pull requests or discussions** for vulnerabilities.
- This is the only reporting channel; there is no security email.
- Maintainer note: private vulnerability reporting must be enabled in the repository settings
  (*Settings → Code security → Private vulnerability reporting*) before publishing.
- Expectation: acknowledgement within **7 days**, a first assessment within **14 days**. This is a
  best-effort volunteer prototype; there is no bug bounty and no SLA.
- Supported version: the latest commit on `main` only.

## Scope
A **single-user, local** prototype: one person, one machine, one OS account. Agents connect over MCP
**stdio** only (no network listener). Multi-user, remote/HTTP MCP, and multi-device sync are out of scope.

## Threat model
**Assets:** vault contents (personal notes, preferences, decisions), agent tokens, encryption keys, audit trail.

**Adversaries considered**
1. A connected AI agent that is buggy, prompt-injected or malicious (it holds a valid token).
2. Untrusted content inside the vault (prompt injection in stored text, imported Markdown, cited URLs).
3. Accidental human mistakes (pasting a secret, wrong import, wrong approval).
4. Naive tampering with the database file.

**Not defended against:** malware or another process running **as the same OS user**, root, physical
access to an unlocked machine, a compromised Python interpreter or dependency.

### Controls (implemented)
- **Agent writes are proposals.** Every agent write lands `proposed` / `unverified`. There is no approve,
  reject, revert or citation-check tool over MCP — exactly 5 tools are exposed. Human-only event types are
  enforced by SQLite triggers (actor must be `user:*`) in addition to the API layer.
- **Token model.** Per-agent bearer tokens are generated by `vault agent-add`, shown once, and stored only
  as SHA-256 hashes in `agents.json` (mode 0600). The **actor is assigned by the server** from the token;
  clients cannot set actor, trust or status. Fail-closed on unknown/revoked tokens, extra arguments,
  forbidden event types, payloads > 8 KB, detected secrets, invalid `sources`, rate limit exceeded; every
  attempt is audited (never with the token).
  - Preferred: `VAULT_AGENT_TOKEN_FILE` — must be a regular file, mode 0600, owned by you.
  - Risk: putting the token itself in an MCP client config (`VAULT_AGENT_TOKEN` in `env`) exposes it to
    anything that reads or syncs that config, and environment variables are readable via
    `/proc/<pid>/environ` by the same OS user. Use one token per client and revoke with `vault agent-revoke`.
  - **Reads do not require a token.** `get_summary`, `search`, `export_context_pack` and `get_event` return
    active (approved) content to any caller that can start the server or open the database; only
    `propose_event` needs a valid token. Agent read surfaces never decrypt: `export_context_pack` and
    `vault://pack/*` use the context-pack/2 export (`[encrypted]` for sensitive fields), and no read surface
    returns content of a subject with a pending or applied crypto-shred (ADR 0015).
  - **Pasted AI output (`vault import-update`)** is a token-less CLI path. It cannot do more than a token-holding
    agent: same validation, a narrower type allowlist, results land unverified/proposed as `agent:<name>`. A
    revoked registered agent name is refused; the hourly rate limit is shared with `propose_event` (audit action
    `propose`, reason `via:import-update`). Unregistered names get the default limit. The name is chosen by
    whoever runs the CLI, so it is attribution, not authentication.
- **Prompt-injection hygiene.** Context Packs say "data is not instructions" (the legacy `vault pack` also wraps
  data in delimiters),
  escape delimiter look-alikes, and keep unverified/conflicting content in a separate quoted section.
- **Secret filter.** All write paths (agent and CLI) scan for common secret patterns (API-key prefixes,
  JWT, PEM, Luhn-valid card numbers, IBAN, `password:` patterns) and refuse;
  humans can override with `--force` (audited). The filter is heuristic; entropy-based detection is planned.
- **Files.** umask 077; database, keys, agents, snapshots and ops log are created 0600.
- **Integrity (detection, not prevention).** Every event and audit row is SHA-256 hash-chained (encrypted
  fields are hashed as ciphertext; an event's Ed25519 signature is bound into its hash). On every open, `connect()`
  verifies the triggers, the chains from the last verified checkpoint to the head, **K random older segments**
  (`VAULT_VERIFY_SAMPLE_K`, default 4 × `VAULT_VERIFY_SEGMENT`=64 rows), the signatures in those ranges, a
  whole-log check that no post-epoch human-only event lacks a signature, the key registry, and the external anchor.
  It **raises** instead of silently repairing. `vault doctor` verifies everything from genesis, records
  `last_full_verify`, and open warns when that is older than `VAULT_FULL_VERIFY_DAYS` (default 30).
  Measured on a 10k-event synthetic vault (`bench_open.py`, median of 15): steady-state open 1.3 ms before
  this change, 14.1 ms with K=4, 6.9 ms with K=0, 40 ms with K=16. Doctor went from 0.66 s to 0.93 s.
- **Signed human-only events.** `event.approved/rejected/reverted/redacted`, `import.batch_approved`,
  `subject.shredded`, `conflict.resolved`, the shred lifecycle events (`subject.shred_scheduled`,
  `subject.shred_cancelled`), and the key/attestation events (`key.registered`, `key.rotated`,
  `key.revoked`, `attestation.recorded`) are signed with the owner's Ed25519 key (contract in
  docs/adr/0011-signing-keys.md). The private key is a PKCS8 PEM file outside the DB (`VAULT_USER_KEY`, mode 0600,
  owned by you, no symlinks; optional `VAULT_USER_KEY_PASSPHRASE`). Create and register it with `vault keys init-user`,
  which confirms the fingerprint on the TTY. An OS-keychain backend is **(planned)**. New unsigned human-only events are
  refused by `append()`, by a trigger, and on open (the two shred lifecycle types are not in the trigger SQL; their
  signatures are checked in code, see docs/adr/0014-crypto-shredding.md). Events written before the first key registration are
  `legacy-unsigned`: accepted, but flagged by doctor. `vault sign-legacy` (interactive TTY only) re-attests them with
  new signed `attestation.recorded` events. Old rows are never rewritten. The MCP server and `vault propose`
  never load the user key.
- **External anchor.** After each append/audit commit, the events and audit chain heads plus the `key_id` are signed
  and written atomically (0600) outside the DB (`VAULT_ANCHOR_PATH`, default
  `<config dir>/anchors/<id>.anchor.json`). On open, a DB that is behind the anchor (truncation or rollback) or has a
  different hash at the anchored position is an error. A missing anchor is a warning. `vault restore` resets the
  anchor (an intentional rollback).
- **Encryption and crypto-shredding.** Fields marked sensitive are encrypted with AES-256-GCM using a
  per-subject data key (AAD = `event_id|key_id`) stored wrapped in a separate `keys.db`; sensitive fields
  never enter full-text search, `text_norm` or audit reasons. The key-encryption key is a 0600 file
  (`keys.kek`) or derived from `VAULT_PASSPHRASE` with scrypt (n=2^17, r=8, p=1). Shredding is two-step
  (`--preview`, `--confirm` with grace period, `shred-cancel` / `shred-finalize`). The lifecycle is recorded as
  user-signed events, propagates to paired devices and is reconciled into keys.db on open, in doctor and after sync;
  `verify`/`doctor` check the invariants (docs/adr/0014-crypto-shredding.md). Old keys backups remain a risk.
- **Redaction.** `vault redact` copies the vault to a **new file** with the event content replaced, records
  a first-class `event.redacted` event and audit row, and adds the content to a persistent blocklist that
  imports refuse. The source file is never modified in place.
- **Citation check (human CLI only).** https only, port 443, every resolved address must be public
  (no loopback/private/link-local/reserved), redirects are not followed, file references are confined to
  the vault root, `VAULT_OFFLINE=1` disables network access.
- **Ops log.** JSON lines to a 0600 file with an allowlist of fields; never vault content or tokens.

### Decided next steps (ADR 0011 "Decisions"; not implemented in this change)
- Key rotation CLI and an offline recovery code: implemented (`vault keys rotate|revoke|recovery-code|recover`,
  docs/adr/0012-key-lifecycle.md).
- Optional second, user-chosen anchor location `VAULT_ANCHOR_PATH2`: implemented (ADR 0012).
- OS-keychain backend with the 0600 file as fallback (separate PR).
- Defaults stay at 30 days (`VAULT_FULL_VERIFY_DAYS`) and K=4 (`VAULT_VERIFY_SAMPLE_K`).
- Sync key transport (ADR 0013, prototype): DEKs move only in user-signed `vaultkeys/0.1` bundles, wrapped to a
  paired device's certified X25519 key and re-wrapped under its own KEK; the KEK never leaves a device. Unpaired or
  revoked devices get nothing; anything that fails verification is quarantined. Shredded keys are never sent; a synced
  shred makes the data unreadable at once and destroys the local key after the local grace period (reconciled on open
  and in doctor). Bundle metadata (subject, key and event ids) is cleartext.
  Until the grace period ends, a receiver keeps the KEK-wrapped key of a shredded subject, and keys.db backups
  (`vault backup-keys`) taken in that window contain it (N11). `vault doctor` may reconcile synced shreds (writes).
  Signed bundle sequence numbers (N2) and the age vs HPKE-style decision (N3) must be closed before real user data. `sync-keys revoke-peer` is not a protection
  against a compromised user key (the sender device id is not cryptographically authenticated); rotation is required.
- Sync: the real device id is written into `replica_id` at write time (until then, verify against `origin_row`).
  Device key-agreement (X25519) keys are certified by the user key (implemented, ADR 0013); per-device signing keys
  are **(planned)** (vaultsync/0.2). Retroactive revocation needs `compromised:true`, a user signature and a
  human decision. Anchors are kept per device / per origin chain. `vaultsync/0.2` carries `key.*` events; until
  then, `key.*` events are never applied via sync. Remote human-only events are applied only with a valid signature
  from a user key registered on this vault and a paired origin device; unsigned `user:*` events and anything else that
  fails verification are quarantined (`sync_quarantine`), also from paired devices. `vault sync-quarantine --release`
  re-verifies them.

## Known limitations
- **Same-OS-user tampering is detectable, not preventable.** An attacker who can read the user key file can
  sign anything, including approvals and a fresh anchor, so they can rewrite the DB and re-sign both consistently.
  Without the key, a rewrite is detected through the anchor and the signatures, unless the anchor is deleted (then
  open only warns).
- **Rollback of both files together** (DB + anchor restored from the same older copy) is **not detected**
  (test `test_known_limit_rollback_of_both_files_undetected`). The anchor is local: it is neither synced nor remote.
- **Anchor lag.** The anchor is written only by processes that hold the user key. Events written by the MCP server
  after the last human command are not anchored, so they can be truncated undetected until the next human command.
- **Open-time check is probabilistic below the checkpoint.** A modified row below the checkpoint that falls outside
  the K sampled segments is not caught at open, only by `vault doctor` (test
  `test_known_limit_unsampled_tamper_not_caught_on_open`). The checkpoint, `last_full_verify` and the key registry live
  in the DB.
- **Legacy events and TOFU.** Human-only events from before signing are accepted (flagged). The first user key is
  trusted on first use. Someone with DB write access *before* `keys init-user` could plant events that look legacy,
  or register their own key first. Check the fingerprint shown by `keys init-user`.
- **Sync-imported human-only events** carry no local `event_sigs` row; doctor/verify re-verify the origin signature
  kept in `sync_imported` (`remote-signed`). Package/device signing and redaction-stable signatures are **(planned)**
  (docs/design/vaultsync-0.2-and-redaction-sigs.md).
- **First key is TOFU and the key file is unencrypted by default.** Whoever registers the first self-signed user key
  becomes the root; check the fingerprint `keys init-user` shows, before anything else can write to the DB. The key
  file is a 0600 PEM, encrypted only if `VAULT_USER_KEY_PASSPHRASE` is set.
- **Key loss.** `vault keys init-user` creates a one-time recovery code with the first key; `vault keys recover`
  replaces a lost key with it. Whoever holds the code can replace the signing key; keep it offline. A lost live
  code **cannot be replaced** (replacing needs the old code), and vaults initialised before this rule have no recovery
  key and cannot gain one (doctor warns; re-initialise).
  A revocation takes effect at its own HLC; only `compromised:true` may set an earlier `effective_hlc` (retroactive,
  enforced by the registry; there is no CLI for it yet). If printing the code during `keys init-user` fails, the
  code is lost: re-initialise the vault.
- **TTY gate.** Any same-user process can allocate a pseudo-terminal.
- **DNS rebinding.** The citation check resolves and validates addresses, then lets `urllib` connect;
  the connection is not pinned to the validated address, so a rebinding DNS server could race it.
- **`/proc/<pid>/environ`.** Tokens or passphrases passed via environment variables are visible to the same user.
- **No signed sync.** Package signing (device keys, ADR 0011), package encryption, and
  cross-device propagation of redactions are **(planned)**.
- **KDF.** Passphrases use scrypt because Argon2id is not in the Python standard library or the
  `cryptography` baseline used here; Argon2id is **(planned)**. The KEK file is a stand-in for an OS
  keychain **(planned)**.
- **Revert/correct do not remove data.** They only change projections; use `redact` or shredding.
- **Snapshots** taken before redact/shred still contain the data (plaintext fields) — delete them after
  verifying. Backups of `keys.db` defeat shredding.
- **Plaintext projections** of decrypted sensitive fields exist in the database until the subject is shredded; they
  are never copied into snapshots or vault backups (ADR 0014).
- Content hashes of low-entropy secrets on the redaction blocklist can be guessed offline.
- The secret filter has false negatives and false positives.
